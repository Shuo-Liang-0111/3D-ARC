# ARC 写实关卡生产

## 执行契约

- 默认工作方式是**初期澄清并确定方案 → 自动生产与内部质量门禁 → 最终交付**。提问集中在初期；已有答案与授权跨轮次、续作和上下文压缩保留。用户已经选定玩法和方案时直接恢复生产，不重走问答。
- 灰模、代表性切片和最终效果由 agent 实际检查、记录和返工，不再等待用户逐阶段批准。仅当用户明确要求分阶段审核时启用相应人工检查点。工具结束、生成排队或构建通过都不是结束任务的理由。
- 用户已要求本技能自动使用 Cardinal。范围内单件、批量、必要补充与质量返工自动登记执行，不再请求使用或批次批准；默认不报告费用。仍读取实际 Cardinal Skill 的 API/凭据合同，遵守服务限制、去重和有限重试；通用批量确认文案不覆盖本项用户授权。
- 主机、账号、工作根目录、项目和部署权限来自**当前任务用户指定与已验证运行状态**，不内置固定服务器，也不把这次的目标写成下次默认值。既有明确用户选择优先于过期仓库/技能默认；只有仍存在无法消解的目标歧义才初期澄清。凭据不进入技能、项目文件、日志或 Git。
- 不修改机器人模型、骨骼、尺寸、初始关节姿态、D435/socket、共享相机算法/FOV、控制映射、运动学或共享包络；不得用关卡专属相机覆盖掩盖场景问题。场景起点、交互高度与布局适配统一机器人合同。
- 以 RF-03 可核实方法与适合目标场景的参考画面为依据；RF-12/RF-13 的历史完成措辞不作为质量证据。整体建筑、材质、设备和交互都须通过正式游戏视觉检查，不能以几件高模替代全场景真实化。

## 1. 初期调查与方案

读 [初期对话](references/approval-workflow.md)、项目实际存在的 `docs/LEVEL_PRODUCTION_STANDARD.md`、`docs/levels/cardinal-realism-handbook.md` 和适用 `AGENTS.md`。将 [任务目标模板](assets/server-profile.json) 复制到任务记录并据当前授权填写；核实服务 PID、cwd、命令行、端口和真实运行时入口，空字段不能当可执行配置。

只有场景描述时，先给 3～5 套不同核心玩法及推荐方案，再分轮询问影响结果的关键问题；用户已有方案则补齐缺失项即可。不把“理解 95%”虚构成测量值。

用 [方案模板](assets/production-plan.md) 明确关卡 ID、玩法、空间尺度、风格、必需资产、性能、机器人冻结、服务器/项目、安装与部署范围、可用替代路线。初期一次确定执行范围；已有“按 v0.1 执行”等指令即是相应方案授权，不另索一次批准。若用户仅要求提案，则交付提案，不擅自进入生产。

## 2. 灰模与内部通路检查

读 [自动化与恢复](references/automation.md)、[生产工具](references/production-tools.md) 及 [RF-13 故障教训](references/rf13-lessons.md)；重建旧关卡时同时读 [早期教训](references/rf03-rf12-lessons.md)。冻结受保护文件当前字节并记录脏改动；建立版本目录和 [资产清单](assets/asset-manifest.json)。

先实现可完成的状态机、尺度正确的灰模和权威碰撞。在独立预览及正式游戏检查起点、完整路线、门窗净空、支撑面、身体与载荷包络。记录实际截图和尺寸；失败自动修正，通过后直接进入真实化，不请求灰模批准。

有余量、奖励或错误惩罚时，读 [余量与容错校准](references/rf13-reserve-lessons.md)。依据用户最新难度要求实测无错误及带错误的完整路线，同时检查途中最低余量和重复领奖；历史参数只作案例，不固化为新关卡默认值。

余量设计采用通用预算闭环：先用真实引擎路线测量移动时间/距离和正确操作次数，再设定移动消耗、错误扣除与正确奖励。移动消耗必须让余量随实际移动明显下降；空交互、错误目标、错误朝向、阻挡放置和重复尝试不能免费。正确操作奖励只按任务节点或物品 ID 首次发放，奖励封顶于初始上限，不能通过重复拾放刷回余量。正常无错误路线应在完成时保留有限容错，不应满余量，也不应在终点前耗尽；通过调整参数使终点余量落在用户要求的容错区间。每次扣费和奖励都在同一状态结算，耗尽时回滚未完成的状态变更并进入失败，完成/失败后冻结，重置清空奖励去重记录。

余量验收至少覆盖：正常完整路线、注入错误后的完整路线、途中最低余量、重复操作、撞墙/阻挡尝试、静止与单独转向、低余量奖励、上限封顶、失败冻结和重置。报告初始值、移动计费单位与单价、错误扣除、正确奖励、终点余量及最低余量；不能只报告终点值或用总时间估算替代真实引擎轨迹。

## 3. 真实化与集成

先生产代表性墙地面、开口、静态设备与关键交互物组成的切片。每件资产隔离检查尺度、正面、结构与材质，再合成并查看正式游戏画面；通过内部门禁后扩展全场景。环境、动态结构、交互 GLB 和碰撞保持可分离、同源布局，统一解码器与强制加载门禁。

| 工具 | 用途与条件 |
|---|---|
| Cardinal | 写实独立道具、高模、可平铺图像；先核实 doctor/capabilities，默认 high-highpoly，不静默降级 |
| Blender | 精确建筑/门窗、尺寸与朝向修整、UV/烘焙、碰撞、GLB；官方版本安装在任务授权根目录的 runtime 下 |
| EmbodiedGen | 仅使用已实测可用且许可适当的图像到物体/静态流程；目录存在不代表生成成功 |
| Three.js / glTF | 继承 ARC 加载、缓存克隆、优化与解码合同，不另造机器人运行时 |
| 浏览器与测试 | 独立预览用于诊断，正式游戏用于验收；必须实际查看截图 |

工具按用途选择，不为凑数量强行调用；替代来源如实登记。资产先写入新候选版本并验证，禁止覆盖正在服务的 GLB 试错。所有生成/归一化/导出/构建脚本使用同一版本参数。

## 4. 自动返工、授权部署与交付

执行 [验收规则](references/acceptance.md) 和 [检查器说明](references/checks.md)。数值/文件检查、完整玩法与正式截图缺一不可；测试须定位当前活动版本，不能继续验证过期灰模。

恢复最终画面验收或迁移版本时，读 [V0.4.1 之后的故障与解决方案](references/rf13-v041-v043-lessons.md)。中途追加奖励、容错或部署要求时更新当前方案并重测受影响项，保留已核实资产与既有授权；分别记录资产版本、玩法规则和代码提交，不能让旧截图或旧参数冒充当前结果。

发现比例、轴向、开口、支撑、材质、穿模或空气墙问题，定位责任层并修复根因，再重测受影响路线和正式截图。已定范围内的建模、布局细化和质量返工自主完成；不通过改变核心玩法、扩大场景、更换主机或修改机器人来绕过困难。

通过内部验收后，在初期已授权部署范围内切换版本，复核线上资产字节与实际画面。按当前仓库/用户规则执行任务范围提交；不把大资产、凭据、环境或日志入 Git，不自行扩大推送权限。

最终直接交付可用 URL、确切版本、实际第一/第三视角及关键交互截图、测试/碰撞证据和已知限制。所有必需门禁通过且授权交付完成才标 `completed`；用户验收单独记为可选 `userAcceptance`，未收到反馈时不冒称用户已接受，也不因此阻塞交付。不再以“候选版等待最终批准”结束默认流程。

## 恢复与真实阻塞

持续更新 [验收与续作记录](assets/acceptance-report.md)：初期授权、当前阶段、task ID、部署版本、缺陷、证据和下一步。续作从记录及线上事实恢复，不从上轮乐观总结恢复。

SSH/截图/服务异常依 [恢复规则](references/automation.md) 分类、等待并在允许范围内重试。只有用户暂停、真实权限/认证阻塞、不可确认的请求受理状态，或有限修复与授权替代均不可行时才报告阻塞；完成不依赖该阻塞的工作。不能绕过工具拒绝，也不能把授权重复询问或缺少证据包装成“自动化完成”。

## RF-15 需求与返工经验

续作 RF-15，或遇到网站/关卡加载失败、方块感、白膜、墙体穿模/闪烁、分步提示清理时，读 [RF-15 需求、问题与解决方案](references/rf15-lessons.md)。其中版本、尺寸、资产数和验证结果是案例事实，不作为其他关卡的固定参数。

- 真实化分别验收结构与材质：镂空、盆腔、支撑、五金需要真实几何；纹理需要在导出的 GLB 和正式浏览器中实际显示。倒角、螺钉或材质命名不能代替验收。
- 墙面闪烁与机器人穿墙分开定位：前者查重复面和共面层，后者查权威布局、碰撞 GLB 与实际物理后端；修复一层不证明另一层通过。
- 导出先确认图片数据、UV、PBR 通道和嵌入缓冲；部署先备齐当前版本的全部依赖，再同步运行入口、资产清单和构建 allowlist，核对源文件/构建/HTTP 字节。
- RF-15 已确认只显示最终任务“将两箱农产品装入冷藏车，并完成出库确认”。清理启动页、常驻面板、场景注入文本与分步弹窗，保留操作控件及必要结果反馈，不删除底层任务状态机。其他关卡按各自用户要求处理。
- 续作以当前活动版本和本轮证据为准；旧验收记录、候选 manifest、引擎通关、浏览器通关和用户验收分别登记，避免把历史结果写成当前已完成。
