# 写实游戏生成 Prompt 与技术验收指南

本文总结 LAAS（[PROJECT_LAAS_v2.md](https://github.com/Braffolk/fable5-world-demo/blob/main/PROJECT_LAAS_v2.md)）的有效经验，并结合本项目的实际问题，形成一套可复用的“生成真实游戏”通用 prompt。

目标不是让某个关卡的单个模型看起来更高清，而是让任意关卡在第一人称或第三人称截图中，经过一秒观察就具备可信的空间、材质、尺度、接触关系和光照层次。

## 核心结论

LAAS 的真实感主要来自完整的实时世界系统，而不是“使用了更高级的 3D 资产”：

- 几何优先：近景由真实轮廓、倒角、碎石、草、杂物和接触细节组成，不能依赖一张地面贴图。
- 多尺度材质：形状、宏观变化、中观磨损、法线、粗糙度和 AO 同时存在。
- 光传输：GI、接触阴影、软阴影、天空反弹光和植物透光决定了物体是否真正落地。
- 环境占用：墙角、缝隙、物体底部和水边都必须有污渍、灰尘、苔藓、磨损或杂物。
- 变化和密度：重复物体需要种子驱动的形状、颜色、年龄、旋转、尺度和磨损变化。
- 视觉回归：每个阶段都必须用参考图对比截图，记录差异并修复影响最大的三项。

LAAS 的文档是规格和验收门，不应直接照搬 4 km 世界、百万级植被等数字。本项目是室内任务游戏，应采用相同原则的缩小版：近景高质量、环境有层次、光照可信、相机统一，而不是盲目追求开放世界规模。

## 本项目的根因判断

### 不是单纯的模型生成失败

本项目已有合理的资产工程边界：GLB、Y-up、米制、底部枢轴、动态/静态拆分、尺寸校验和程序化回退。这些解决了“能否稳定运行”，但没有解决“是否像真实场景”。

### 当前最大的视觉问题

1. [game/app.js](../game/app.js) 使用 WebGLRenderer、单个主光和半球光、PCF 阴影与 ACES，缺少 GI、GTAO、接触阴影、TAA、自动曝光和体积效果。
2. 多个环境仍由 Box/Cylinder/Plane 组成；GLB 主要提升交互道具，无法替代墙角、地面、设备之间的环境细节。
3. RF-01 主要只有 Base Color 贴图；没有成套 Normal、Roughness、AO、Height、污渍和湿润层。
4. RF-02 的运行时流程将许多高模简化到约 2%–6% 几何比例，并将纹理压缩到 WebP/512–1024，近景轮廓和微结构会明显损失。
5. 生成 prompt 偏向“孤立产品摄影”：适合单个道具，不足以描述安装关系、接触面、材质变化、场景上下文和多视角可见性。
6. 现有测试主要检查状态机、路径、包围盒、GLB 加载和构建，没有参考图差异、阴影颜色、材质通道、重复性、三角形预算和裸地检测。

因此，正确的改进对象是完整链路：

```text
参考图/设计意图
  -> 资产与环境生成
  -> LOD、UV、PBR 烘焙
  -> 场景组合与接触细节
  -> 相机/灯光/后处理
  -> 浏览器截图验收
  -> 差异修复与回归
```

## 通用视角架构

第一人称和第三人称不应该按关卡各自设计，而应共享同一套“视角契约”：

- 世界坐标、单位、重力、碰撞和角色朝向始终一致。
- 第三人称相机是角色根节点外的可碰撞跟随相机，支持距离、肩位、俯仰和遮挡处理。
- 第一人称相机挂在角色头部/传感器挂点，使用同一角色朝向、移动速度和碰撞结果。
- 两种相机只改变观察位置、视场角和角色可见性，不改变场景灯光、材质、LOD、阴影或交互规则。
- 相机切换必须保持投影、曝光、雾、LOD 和阴影稳定，不能因视角切换出现明显弹出或亮度变化。
- 所有截图验收至少包含一个第一人称近景和一个第三人称环境构图。

## 可直接复用的通用游戏生成 Prompt

```text
你是一名资深实时渲染工程师、技术美术、关卡设计师和视觉 QA 工程师。
请为现有项目生成一个可玩的真实感网页游戏，不要只生成一个好看的静态场景。

目标：
玩家在第一人称和第三人称下看到的每一张关键截图，都要在一秒内具备可信的
空间尺度、材质反应、接触关系、光照层次和环境密度。先保证近景和主要构图，
再扩展中远景。不要用“photorealistic”这一词代替具体的几何、材质和光照工作。

开始前：
1. 读取现有代码、关卡尺寸、碰撞、角色挂点、相机参数、资源 manifest、测试和参考图。
2. 保留已有状态机、交互规则、坐标约定、可达性和任务逻辑。
3. 把视觉系统、资产系统、相机系统、玩法系统和 QA 工具拆成可维护模块。

几何与环境：
1. 所有近景物体必须有真实轮廓、厚度、倒角、缝隙、连接件和受力关系。
2. 近景地面不能只是颜色贴图；加入碎屑、磨损、接触污渍、边缘堆积和必要的真实几何。
3. 墙角、物体底部、设备连接处、门槛、管线和遮挡区域必须有环境占用和接触细节。
4. 重复物体必须有种子驱动的形状、旋转、尺度、颜色、年龄、磨损和局部破损变化。
5. 场景中的家具、设备、道具和建筑必须遵循统一的现实世界尺寸和材质逻辑。

材质：
1. 每个材质同时提供 Base Color、Normal、Roughness、Metallic、AO，以及需要时的 Height/Mask。
2. 每种材质必须有宏观变化、中观磨损和微观表面反应，禁止单一噪声或明显平铺。
3. 污渍、锈蚀、灰尘和湿润必须与重力、接触、排水、使用频率和朝向相关。
4. 不烘焙不可控的灯光、阴影、反射或工作室背景；这些由运行时渲染器负责。

资产契约：
1. 资产使用 Blender 程序化、扫描、公开授权素材或 AI 生成均可，但必须经过人工/脚本验收。
2. 每个资产输出 LOD0、LOD1、LOD2；近景不得使用会破坏轮廓的极端减面比例。
3. 记录尺寸、三角形数、材质通道、纹理尺寸、UV、包围盒、枢轴和碰撞代理。
4. 道具可以独立生成，但必须在真实游戏相机、真实灯光和真实摆放关系下验收。
5. 环境资产必须考虑安装面、地面接触、背面、阴影接收和与邻近资产的连接。

渲染与相机：
1. 默认使用 Three.js WebGPURenderer + TSL；若必须保留 WebGL，明确每个替代方案和质量损失。
2. 使用 HDR/IBL、物理曝光、软阴影、接触阴影、GTAO、TAA/TRAA、Bloom 和适度体积雾。
3. 第一人称和第三人称共享坐标、碰撞、灯光、材质、LOD、阴影和交互，只改变观察相机。
4. 第三人称相机处理角色遮挡和墙体穿透；第一人称相机使用稳定的头部/传感器挂点。
5. 相机切换、窗口尺寸变化和视场角变化不能造成明显的亮度跳变、LOD 弹出或阴影跳变。

验收闭环：
1. 启动真实浏览器，使用固定相机和自由相机分别截图。
2. 将截图与参考图并排比较，列出最重要的十个视觉差异并按影响排序。
3. 每轮只修复影响最大的前三项，然后重新截图和回归。
4. 检查 FPS、CPU/GPU 时间、绘制调用、三角形、纹理内存、阴影颜色、重复特征和材质通道。
5. 禁止用雾隐藏空场景、黑色环境阴影、纯色盒体、规则复制、过度压缩近景资产和“以后再做”的 TODO。

交付：
代码、资源 manifest、LOD/材质报告、截图对比、差异记录、性能数据、已知偏差和下一轮修复项。
```

## 3D 资产生成子 Prompt

```text
生成可直接用于实时游戏的 [物体名称]，真实世界尺寸为 [宽] x [高] x [深] 米。

这是一个真实使用中的 [工业/家庭/实验室] 物体，不是展示台上的孤立概念模型。
保留真实厚度、倒角、连接件、螺丝、缝隙、装配关系、受力结构和可见背面/底部。
它将与 [地面/墙面/设备] 接触或安装，请为接触面、遮挡、阴影接收和连接处建模。

要求 Y-up、前方 +Z、米制、底部中心枢轴、干净 watertight topology、可用 UV、LOD0/1/2，
并提供 Base Color、Normal、Roughness、Metallic、AO、Height/Mask 和材质分区。
磨损、灰尘、锈蚀和湿润必须出现在真实使用位置，不要全表面随机噪声。
近景轮廓必须由真实几何决定，不能只用法线贴图伪造。
不要烘焙灯光、阴影、反射、地板、房间、人物、logo、文字、水印或额外物体。
在目标游戏相机和实际运行时灯光下输出预览，并附三角形、纹理、材质和包围盒报告。
```

## 实施优先级

### P0：对一秒真实感影响最大

- 选定一个代表性关卡，建立第一人称/第三人称固定截图基线。
- 停止对近景统一使用 2%–6% 的极端简化比例。
- 为地面、墙面、设备和关键道具补齐 Normal/Roughness/AO/Decal。
- 增加 IBL、接触阴影、GTAO、TAA 和合理曝光。
- 给环境增加墙角、地面接触、污渍、遮挡、管线和杂物。

### P1：形成可复用的写实资产管线

- Blender 程序化模块、扫描资产和 AI 资产统一转换为同一 GLB/PBR/LOD 契约。
- 近景、中景、远景分别设定三角形和纹理预算，而不是对所有资产使用同一压缩比例。
- 为相同类别资产生成变体和种子化摆放。
- 增加 reference-delta、材质通道、阴影颜色、重复性和截图回归测试。

### P2：性能和规模

- 在画面基线稳定后再引入 WebGPU、GPU 散布、实例化、异步加载和更复杂的 LOD。
- 优化应优先减少重复计算和过度绘制，不能先缩短可见距离、降低密度或用雾遮挡。
